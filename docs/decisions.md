# 负责人决定记录

按时间顺序记录产品负责人做出的决定。引号里是负责人的原话。新的决定加在末尾，不改旧条目。

## 2026-11-17

1. 项目是什么：“趣味历史学习项目：把历史和地理结合起来，用一个历史名人的旅途/人生轨迹来引导用户学习历史地理文化艺术科学知识。”
2. 受众：“全年龄、亲子共用。”
3. 内容：“以精心编写的内容为主、AI 只做答疑。”
4. 视角：“让用户直接成为历史名人本人，体验当时的历史背景，地理人文。”
5. 目的：“让用户不但熟悉了历史事件，而且理解了发生这些事件的原因。”
6. 形态：“这不是一个游戏，而是一个知识学习的网站。用户通过选择不同的历史名人，了解他们的故事和轨迹从而学习历史地理人文科学知识。”
7. 设计上的三条提醒：“不要刻意去解释为什么。”“不要刻意连接人物。”（原话写作“不要可以连接人物”，按“刻意”理解。）“不要刻意追求天马行空。”
8. 工作顺序：“你应该先把整体设计给我审核，通过了再出一个原型demo。而不是现在就开始在细节上纠结。”之后又依次要求审核技术选型和部署方案，都通过后才开始制作。
9. 地图：所有人物共用一套地图引擎；“我倾向于全程三维，这才能方便用户理解地形。”
10. 整体设计：通过（“没有了，通过”）。见 `overall-design.md`。
11. 技术方案：通过。见 `technical-plan.md`。
12. 部署：“用我们之前做的另一个项目——象棋游戏的部署方案”，确认“就用这套”。见 `deployment.md`。

13. 三维地图引擎：MapLibre GL JS（“用 MapLibre 开工”）。依据是引擎验证的对比结果：功能条目两边大多通过，MapLibre 体积更小、地名能力现成。真机流畅度当时没有测到（开发用的机器没有显卡），留到原型在平板和手机上确认；如果不流畅，在地图适配层后面换引擎。

14. 原型发布到网上供审核（“发布到网上”）。原型做完后负责人还没有审核内容和界面，发布是为了能在平板和手机上看，不代表原型已经通过。仓库是公开的。

15. 对原型的意见：“现在的问题是demo的美术风格和设计水准太次，整个界面没有任何吸引人的地方。我建议把地图引擎换掉。自己做地图，场景。”随后选定：画面风格用“立体沙盘”（像博物馆里的微缩沙盘：真实地形做成立体模型，城、楼、亭、船、田是小模型，每位人物按自己的时代配色和题字）；场景做到“每站一个场景”（真实地形上摆建筑，镜头跟着正文一节一节带着看，有的地方会动，比如徐州的水涨到城下）。场景里不做小人、车马的活动。已发布的原型在负责人的设备上三维地图是流畅的。下一步先出风格样张给负责人挑，定了再改整体设计和技术方案，然后重做。

## 2026-11-18

16. 风格样张：做了三套“立体沙盘”样张（素模、设色、微缩），负责人选定“设色”（“用设色”）：沙盘用宋代青绿山水的颜色，地名用竖排题签加红印，沙盘装在木框里，页面是宣纸底、标题用楷体。样张在 `spikes/art-direction/b`。选定的是画面风格；样张里的河道、城墙、堤、水位是示意，黄楼的样子没有考证，也没有在平板和手机上跑过。下一步改整体设计和技术方案给负责人审，通过后才重做。

17. 改过的整体设计和技术方案：通过（“通过”）。两份文档“请负责人定”里列的各项随之确定：全程沙盘和各站沙盘分成两级，中间是切换，路段的沙盘先不做；进一站先看来路；楷体换成开源的霞鹜文楷；沙盘上的考证由制作方查公开史料并写明出处，查不到的标示意，没有专业的人审校；三维画面底层用 three.js；重做按技术方案第九节的顺序，先做第 0 步（样张上真机、全程沙盘样张）。把样张发到网上仍要负责人另说“发布”。
