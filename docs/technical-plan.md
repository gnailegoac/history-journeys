# 技术方案

状态：负责人已审核通过（2026-11-17）。三维地图引擎已在“引擎验证”之后确定为 MapLibre GL JS，见 `decisions.md` 第 13 条。

## 一、工程思想

1. **内容与程序分离，数据驱动。** 网站是一个“阅读器”，人物是数据。加一位人物只加内容文件，不改代码。
2. **契约先行。** 人物、轨迹、站点、小注、镜头长什么样，先用一份数据规格定死。程序和内容都以它为准，并由工具自动校验。
3. **纵向薄切片，逐步放宽。** 先把“一位人物、一站”从内容到三维地图到页面完整做通，再加站、加人物。每一步结束都有能打开看的东西。

## 二、架构

纯前端静态网站，没有服务器、数据库和账号。只有 AI 答疑将来需要一个很薄的服务端接口。

```
内容层      每位人物一个文件夹：人物资料、轨迹、各站正文、图片
   │  构建时按数据规格校验
数据与领域层  读取内容；人物、轨迹、站、小注的纯逻辑
   │
界面层      首页 · 人物页 · 站点页 · 讲解员面板
   │                    │
地图适配层              答疑适配层
   │                    │
三维地图引擎            原型：占位；以后：服务端接口
```

页面只对适配层说“飞到这一站”“画出轨迹”，不直接碰地图引擎。以后换引擎或换大模型，只动一个模块。

## 三、分层

| 层 | 负责什么 | 怎么测 |
|---|---|---|
| 内容层 | 人物资料、轨迹坐标、各站正文、小注、图片、凭据 | 自动校验：格式、坐标是否合理、站点顺序、小注能否在正文里找到、凭据是否填写 |
| 数据与领域层 | 读取内容，以及不依赖界面和地图的纯逻辑 | 单元测试 |
| 地图适配层 | 唯一接触地图引擎的代码 | 浏览器自动测试，加帧率和加载时间测量 |
| 界面层 | 三种页面和讲解员面板 | 浏览器自动测试走通主流程 |
| 外部服务 | 地形数据、底图、将来的大模型 | 集中在一处配置，各备一个替代方案 |

依赖只能从上往下；内容里不出现代码。

## 四、防止风险和失控的原则

1. **分阶段审核，不越级。** 整体设计、技术方案、引擎验证、原型、扩充内容，每一关负责人通过后才进下一关。
2. **范围锁定。** “暂不做”清单有约束力；过程中冒出的新想法记入待办，不混进当前这一步。
3. **小步，随时可运行。** 每次改动都小，主干任何时候都能打开运行。
4. **用证据说话。** “完成”的标准是自动测试通过加浏览器实测；没验证的地方明说。
5. **单一事实来源。** 设计决定和数据规格各只有一份，放在 `docs/` 里；要改先改文档。
6. **易变的部分隔离。** 地图引擎、地形数据源、大模型都在适配层后面。
7. **性能有预算。** 三维地图在平板上的加载时间和流畅度先定指标，引擎验证阶段就测，不达标先解决。
8. **史实有红线。** 没有填写凭据的内容通不过校验；AI 不生成正文。

## 五、具体选型

| 项目 | 选择 | 备选 |
|---|---|---|
| 语言 | TypeScript（严格模式） | 无 |
| 构建工具 | Vite | 无 |
| 界面框架 | React | 不用框架，纯 TypeScript |
| 三维地图引擎 | MapLibre GL JS（引擎验证后由负责人确定，2026-11-17） | CesiumJS |
| 地形数据 | 开放的全球高程瓦片 | 自建瓦片 |
| 底图 | 自己配色：按高程着色加地形晕渲，叠加河流和海岸线 | 卫星影像 |
| 内容格式 | 结构用 JSON，正文用 Markdown | 无 |
| 测试 | Vitest（单元）加 Playwright（浏览器） | 无 |
| AI 答疑 | 原型只做界面；以后加薄的服务端接口，只依据站内内容回答 | 无 |
| 部署 | 静态文件，见 `deployment.md` | 无 |

## 六、最大的三个风险

- **全程三维在平板和手机上的流畅度。** 引擎验证阶段实测。
- **地形和底图依赖外部的开放服务。** 原型不受影响；以后自己托管瓦片时只打包轨迹沿线的范围。
- **内容产能。** 每位人物约八站，每站约千字且要有凭据。
