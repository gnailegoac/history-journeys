# 引擎验证：MapLibre GL JS 6.18.0

测量时间 2026-11-17。所有数字都是本机实测，出处见 `metrics.json` 和 `tests/out/*.json`。

## 先看这三点

1. **功能上十条都能做出来。** 地球到山谷是同一个地图对象、同一套样式，三峡、大庾岭的山体立得起来，轨迹贴地，中文地名不需要字体服务器。
2. **本机没有显卡，帧率数字只能说明软件渲染下的情况。** 无界面 Chromium 拿到的渲染器是 `ANGLE (Microsoft, Microsoft Basic Render Driver (0x0000008C) Direct3D11 vs_5_0 ps_5_0, D3D11)`，即 CPU 渲染（本机显示适配器只有 Microsoft Basic Display Adapter 和 AWS Indirect Display Device）。在这种条件下飞行平均 5.5 帧、最低 0.76 帧。“硬件加速下不低于 30 帧”这一条**没有条件验证**，不能算通过。
3. **三维地形是开销的大头。** 同一段飞行关掉三维地形后是 15.6 帧，开着是 3.4 帧（当时机器上还有别的测试在跑，只看相对关系）。

## 怎样运行

```
cd spikes/maplibre
npm install
npm run dev        # 开发模式，http://localhost:5411/
npm run build      # 类型检查并构建到 dist/
npm run preview    # 用构建结果起服务，http://localhost:5411/
```

实测脚本（先起 `npm run preview`；第一次要 `npx playwright install chromium`）：

```
node tests/tour.mjs        # 冷启动、八站飞行、三个检验视角；写 tests/out/tour.json 和大部分截图
node tests/checks.mjs      # C1 连续缩放、飞行途中截图、古今地名、鼠标和触摸；写 tests/out/checks.json
node tests/experiment.mjs  # 关掉场景的各部分比较帧率；写 tests/out/experiment.json
node tests/report.mjs      # 汇总成 metrics.json，并统计 dist/ 的体积
```

每个脚本都是无界面运行，自带不到 5 分钟的强制超时。

## 实测数字（C8）

条件：`vite preview` 提供的生产构建；视口 1440×900，像素比 1；Playwright 1.65.0 的无界面 Chromium 158.0.8127.18，启动参数 `--use-angle=d3d11 --enable-gpu --ignore-gpu-blocklist`；每次都是新的浏览器环境（HTTP 缓存为空）；CPU 是 16 线程的 Xeon Platinum 8488C，没有显卡。这一轮开始前和结束后机器上没有别的无界面浏览器在跑（CPU 占用读数 20% 和 8%），中间没有监视。

- **首个可用画面**（从开始导航到 `__spike.ready`：地图加载完、水体图层加上、第一次空闲）：3735、2837、2830 毫秒。此时已下载 88 张高程瓦片，4.5 MB。
- **飞行帧率**（只算镜头动画那一段，八段合计）：平均 5.5 帧，最低 0.76 帧（最低 = 1000 ÷ 最长一帧的毫秒数）。

- **帧时间花在哪**（汴京和黄州之间来回飞，瓦片已缓存，机器当时繁忙，只看相对关系）：完整场景 3.4 帧；去掉粗略底色层 3.6；去掉地形明暗 3.6；去掉按高程着色 4.6；去掉水体 3.1；**去掉三维地形 15.6**。

## 遇到的限制

1. **本机没有显卡。** 上面所有帧率都是 CPU 渲染的结果，不能拿来推断平板和手机。另一种无界面模式（`channel: 'chromium'`）在本机启动失败（`spawn UNKNOWN`），所以只测了默认的 headless shell。
2. **三维地形贵。** 引擎把所有图层先画到地形瓦片的贴图上，再加深度和坐标两遍，CPU 渲染下帧率降到四分之一左右。在真机上占多少要另测。
3. **飞行途中瓦片跟不上。** `shots/flight-mid.png`：大部分地面是粗略的底色（我为此加了一层只到 z5 的底色层，否则没到的地方会露出背景色，看上去像海），前方的轨迹线也还没画出来，线断在已加载瓦片的边上。引擎没有“沿路线预取瓦片”的接口。帧率正常时会好多少没有验证。
4. **贴地线的瑕疵。** 线宽按每块地形瓦片各自的比例画，远近两级瓦片的接缝处线宽有台阶（`sanxia.png`、`dayuling.png`、`c1-zoom-4km.png`），接缝上偶尔有小碎片（`stop-bianjing.png`）。近处的线因为透视会很宽。另外途经点之间是直线，所以线会翻山而不是沿江，这是数据的简化。
5. **高程数据只有 30 米一格。** 离地 5 公里以内山体发虚。高程是 2000 年前后测的，水体轮廓是现在的，三峡库区的蓝色会爬到岸坡上一点。
6. **水体从 zoom 10 才出现**，是我为了省流量只取 z10 一级瓦片的结果（之前取 z6 到 z12 时一趟巡览要 31.5 MB），缩放经过 zoom 10 时河湖是突然出现的。矢量瓦片里带着道路等用不上的图层，所以单张不小。
7. **地球阶段没有雾。** 控制台有一条警告 `calculateFogMatrix is not supported on globe projection`，放大转成平面投影后雾才生效。
8. **文档写明倾角大于 60 度属于实验性质。** 这里用到 62 到 70 度，没看到问题，但不在引擎的保证范围内。
9. **中文字体的坑。** `localIdeographFontFamily` 只在图层用默认 `text-font` 时生效；一旦自己写 `text-font`，引擎会把它当作 CSS 字体名去画，写错了字会变得极小。现在的地名是常规字重。
10. **地名会被地形遮挡**（引擎的行为）。八站的预设镜头下没有发生，换别的镜头位置时目标站地名有可能被山挡住，没有逐一排查。
11. **`getState().distanceKm` 在地球阶段不是真实距离**，是按平面投影换算的值；近景下与预设一致（误差 0）。

## 用于本项目的利弊

有利：

- 地球、地形、明暗、按高程着色、天空都是样式里的声明，整张底图只有几十行；从地球到山谷不用换引擎或换模式。
- 地名是现成的符号图层：中文本地绘制、自动避让、朝向屏幕、落在地形高度上，古今切换是一次 `setLayoutProperty`。
- 线和面自动铺在地形上；鼠标和触摸手势（含双指倾斜）都是内置的。
- 镜头模型就是“中心点 + 缩放 + 倾角 + 朝向”，与每站的 `distanceKm / pitch / bearing` 直接对应，到站误差为 0。
- 体积小：JS 合计 gzip 后 441 KB。BSD 三条款许可，不需要任何账号。

不利：

- 三维地形的渲染开销大，而且本次没能在有显卡的设备上验证；全站“全程三维”压在这一点上，定引擎之前必须在平板和手机上再测。
- 没有沿路线飞行的现成接口，这里是自己每帧 `jumpTo` 写的（连路径取样约一百行）；也没有预取瓦片的接口。
- 贴地线有接缝台阶，想要更讲究的轨迹（立起来的线、带箭头的三维路径）得自己写自定义图层。
- 地形只能来自栅格高程瓦片，精度受数据限制；文档里有 quantized-mesh 的例子，没有试。
- 6.x 是新的大版本：只有 ES 模块、必须 WebGL2、配合打包工具要手动 `setWorkerUrl`，网上多数资料还是旧版本的写法。
- 一趟巡览约 51 MB 瓦片流量，主要是高程 PNG（平均约 45 KB 一张）。正式做的话要考虑自己切一套更省的高程瓦片。
